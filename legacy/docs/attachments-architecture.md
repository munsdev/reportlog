# Attaching evidence to a report

Architecture note — how photos, video and documents can ride on an incident
report without breaking the append-only hash chain, the Tier A / Tier B split,
or the EU-only footprint. Systems only; legalities are handled separately.

Status: **Photos and video are both built, behind a feature flag.** See
the Attachments section of the README for what shipped and how to switch
it on. Phase 4 (offsite replication, dedup, browser-side encryption) is
still design.

The phasing below proved right in one respect and wrong in another. Right:
doing images first answered every hard architectural question at a tenth
of the operational weight. Wrong: it split HEIC and video into separate
phases, when they turned out to be *the same problem* — neither can be
made safe by trimming metadata, so both needed the decode-and-re-encode
step. Adding that once covered both.

Three things changed between this design and the implementation, all
noted inline in §3 and §7:

- The per-object data key lives on `attachment_heads`, not `attachments`.
  It has to be destroyable for crypto-shredding to be a cryptographic fact
  rather than a promise about deleting ciphertext, and the chained table
  is append-only.
- `exif_enc` is encrypted under that per-object key rather than the master
  key, so destroying it takes the GPS with the pixels.
- Uploads are authorised by a server-issued *draft* token, because they
  begin while the reporter is still typing — before `POST /api/reports`
  has staged anything for a submission token to exist.

## 1. What we are actually adding

Today a report is a row: structured fields plus a narrative, canonicalised with
JCS, SHA-256'd, and welded into a global hash chain that gets an RFC 3161
timestamp from DFN every night. Every property the project sells —
tamper-evidence, survivability under seizure, a §1746 declaration a reporter can
print — comes from that row being small, textual, and immutable.

An attachment is none of those things. It is large, opaque, generated by a
device we do not control, and it carries far more identifying information than
anything currently in Tier B. A photo of a polling place contains GPS
coordinates, a camera serial number, a timestamp the reporter did not choose to
disclose, and the faces of bystanders who never consented to anything.

So the goal is not "add file uploads". It is: **extend the existing evidentiary
guarantees to bytes, while extending the existing privacy guarantees to the much
sharper disclosure risk those bytes carry.** Nearly every decision below falls
out of that sentence.

## 2. The constraints the codebase already imposes

Five existing decisions are load-bearing. Anything that fights them is the wrong
design.

| Existing property | What it forces on attachments |
| --- | --- |
| `reports` is append-only by trigger; `content_hash` covers the submitted fields | The set of attachments must be fixed when a version is written. Adding a file later cannot be an `UPDATE` — it has to be a new version in the thread. |
| Nothing enters the chain until the confirm link is clicked | Files are uploaded *before* the email is verified. They need a staging home with a TTL and a hard quota, exactly like `report_submission_tokens`. |
| Tier A public / Tier B encrypted, moderator-only, every read written to `access_log` | Original bytes are Tier B or stricter. Only a derived, stripped, individually-approved rendition can ever be Tier A. |
| Publish gate is `withdrawn = false AND moderation_status = 'valid'` | Media needs its own second gate on top. A report can be publishable while its video is not. |
| One modest shared box, single Node process, `express.json({limit:'256kb'})`, other services alongside it | Large bodies must never traverse the app process, and transcoding must never run in it. |

The codebase already solved "immutable record with mutable judgement attached"
once: `reports` (chained, frozen) beside `report_heads` (pointer, status,
severity, no trigger). Attachments should reuse that shape rather than inventing
a second idiom.

## 3. Data model

Three tables. Two split along the same seam as `reports` / `report_heads`: what
the file *is* (frozen, chained) versus what we have *decided* about it (mutable,
moderator-driven). The third says which **versions** of a report carry which
files, which is not the same question as which version a file arrived with — see
the correction note in §4.

```sql
-- Immutable. Append-only trigger. Digests here enter the report's content_hash.
CREATE TABLE attachments (
  id             bigserial PRIMARY KEY,
  thread_id      uuid NOT NULL,          -- the report lineage it belongs to
  report_id      bigint NOT NULL         -- the version it FIRST arrived with.
                   REFERENCES reports(id),  -- NOT the set that carries it: that is
                                            -- report_attachments, migration 033.
  ordinal        int NOT NULL,           -- display order, unique within the THREAD
  original_name  text,                   -- as given by the uploader, never trusted as a path
  media_type     text NOT NULL,          -- sniffed server-side, not the browser's claim
  byte_size      bigint NOT NULL,
  sha256         text NOT NULL,          -- of the ORIGINAL plaintext bytes, pre-encryption
  storage_key    text NOT NULL,          -- object key in the evidence bucket
  captured_at    timestamptz,            -- from container metadata, if present
  exif_enc       bytea,                  -- stripped metadata, encrypted UNDER THE DEK; GPS lives here
  received_at    timestamptz NOT NULL DEFAULT now()
);

-- Which versions commit to which files. Append-only.
--
-- A correction carries a file forward by writing another row HERE rather than
-- copying the attachment: a copy sharing the storage key would outlive the
-- crypto-shred of the original and hold a live key to a deleted object. One
-- file is one row for as long as it exists, so destroying its key destroys it
-- from every version — which is the only thing erasure can honestly mean.
CREATE TABLE report_attachments (
  report_id      bigint NOT NULL REFERENCES reports(id),
  attachment_id  bigint NOT NULL REFERENCES attachments(id),
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (report_id, attachment_id)
);

-- Mutable pointer layer. NO append-only trigger, same call as report_heads.
CREATE TABLE attachment_heads (
  attachment_id    bigint PRIMARY KEY REFERENCES attachments(id),
  scan_status      text NOT NULL DEFAULT 'pending'
                     CHECK (scan_status IN ('pending','clean','infected','unreadable')),
  publication      text NOT NULL DEFAULT 'withheld'
                     CHECK (publication IN ('withheld','published','refused')),
  dek_wrapped      bytea,                -- per-object key, AES-256-GCM under the master key
  rendition_key    text,                 -- stripped derivative in the public bucket
  alt_text         text,                 -- moderator-authored, required to publish
  dek_destroyed_at timestamptz,          -- crypto-shredding; see §7
  updated_at       timestamptz NOT NULL DEFAULT now()
);
```

Note what is deliberately *not* in `attachments`: no approval flag, no scan
result, no rendition. Those are judgements that change, and putting them in a
chained table would make every moderator click a chain event.

The wrapped data key sits with them, for a different reason found while
building: `attachments` is append-only by trigger, so a key stored there could
never be zeroed — and "erased" would then mean "we deleted the ciphertext"
rather than "the content is cryptographically unrecoverable". Nothing
evidentiary is lost by moving it, because the digest is what the chain commits
to and the key was never part of that claim.

Two smaller changes fall out:

- `access_log` needs to cover attachment reads — either a nullable
  `attachment_id`, or a `subject_type` / `subject_id` pair if we would rather
  generalise it now.
- `self_service_log`'s action vocabulary gains `'media'`, so publishing or
  refusing a file carries the same mandatory written reason every other
  moderator action already does.

## 4. Keeping the chain honest

A digest that is not in the chain is not evidence — it is a claim the server
makes about itself. So the attachment manifest goes inside `content_hash`,
computed in `insertReportVersion` alongside everything else:

```js
const immutableFields = {
  public_ref: publicRef,
  received_at: receivedAt,
  thread_id: threadId,
  corrects_id: correctsId,
  // ordered list, each entry { ordinal, sha256, byte_size, media_type }
  attachments: attachmentManifest,
  ...fields,
};
```

Because JCS canonicalisation is already the documented serialisation, this needs
no new hashing story — the manifest is just more JSON, and the nightly DFN
anchor already covers it. The claim the system can then make is precise: *this
exact file, byte for byte, existed and was associated with this report before
this timestamp.* That is the same claim the text already makes, which is the
point.

**The consequence people will trip over:** adding a photo to an existing report
is a **correction**. It writes a new `reports` row with `corrects_id` set,
advances the head, and — per the existing rule — resets `moderation_status` to
`pending`, pulling a live report off the public board until it is re-approved.

> **And a correction carries the files it already had.** This did not work until
> migration 033: the correction path passed no manifest, so the new version's
> hashed object had no `attachments` key, every file read joined against the new
> version and found nothing, and a reporter fixing a typo lost their video —
> silently, and while verifying perfectly, which is why it went unnoticed. A
> correction now inherits the previous version's files by linking them, and the
> manifest it seals is byte-identical when only the text changed.

That is correct behaviour, not a bug: the version that was published did not
contain that file, and the archive should say so. But it is a genuinely
surprising UX outcome, and the interface has to say it out loud before the
upload starts (§9).

The reverse case — a moderator refusing to publish a file — must never remove it
from the manifest. Refusal is a `publication = 'refused'` flag on the head; the
digest stays in the chain forever. The archive records that the file was
submitted even when the public never sees it, and that asymmetry is exactly what
makes the counts in `/api/stats` trustworthy.

## 5. Where the bytes live

All three realistic options are Hetzner and therefore EU-resident. They are not
interchangeable.

| Option | Locations | Interface | Fit |
| --- | --- | --- | --- |
| **Object Storage** — *primary* | Falkenstein, Nuremberg, Helsinki | S3-compatible (Ceph RGW): presigned URLs, multipart | The only option with a presigned-upload story, which is the whole reason the app process stays out of the data path. Roughly €6/TB-month at list, including 1 TB egress. |
| **Storage Box** — *cold copy* | Falkenstein, Helsinki | SFTP / rsync / Borg / SMB | No object API, so useless as a live backend — but ~€4/TB-month for a nightly Borg push of the encrypted originals. Cheapest credible answer to "the primary bucket is also a single point of failure." |
| **Local volume** — *no* | The shared box | Filesystem | Puts hundreds of GB on a box also running other services, makes backup our problem, and dies with the server — precisely the scenario the transparency log exists to survive. |

(Prices are list at time of writing and should be re-checked before commitment.)

### Two buckets, not one

The bucket boundary should carry the Tier A / Tier B boundary, because a single
bucket with per-object ACLs is one misconfiguration away from publishing an
unreviewed video.

- `S3_BUCKET_EVIDENCE` — original bytes, envelope-encrypted, **no public access,
  ever**, no presigned reads issued to browsers. Reachable only by the app and
  the media worker.
- `S3_BUCKET_RENDITIONS` — derived, metadata-stripped, moderator-approved files only.
  An object appearing here *is* the publication decision.

Plus a short-lived `S3_BUCKET_STAGING` prefix or bucket with a 48-hour lifecycle rule
matching the confirm-token TTL, so abandoned submissions expire without a cron
job to forget to write.

## 6. The ingest path

The browser talks to Hetzner directly; the app issues permission and records
outcomes but never carries the payload. Everything hostile — sniffing the real
type, scanning, decoding, transcoding — happens in a separate worker process
that is allowed to crash.

```
  Browser ──multipart──▶ S3_BUCKET_STAGING ──pulls──▶ media worker ──▶ S3_BUCKET_EVIDENCE
     ▲                   (SSE, 48h)            (sandboxed:        (encrypted
     │                                          scan · strip ·     originals,
  presigned                                     encode ·           never public)
  PUT grant                                     envelope-encrypt)
     │                                                │    └──────▶ S3_BUCKET_RENDITIONS
     │                                                │             (stripped, approved)
  Express app ◀──manifest into content_hash──── Postgres
  (no payload bytes)                            (digests + wrapped keys)
```

Moderator reads go the other way: the app streams from `S3_BUCKET_EVIDENCE`, decrypts
in flight, and logs.

1. **Request a slot.** `POST /api/uploads` with declared filename, size and
   type. The app enforces a per-token quota (say 10 files / 500 MB), checks the
   extension allow-list, and returns a presigned multipart URL scoped to one key
   under the staging prefix. The submission token is the authorisation — no
   login required, same as the form itself.
2. **Upload direct to Hetzner.** Multipart, so a dropped connection on rural
   mobile resumes instead of restarting. nginx never sees it; `express.json`'s
   256 kB limit stays exactly where it is.
3. **Worker claims it.** A separate systemd unit — non-root, network restricted
   to the S3 endpoint, `MemoryMax`, `TasksMax`, seccomp — pulls the object and
   does the untrusted work: magic-byte type sniffing (the browser's
   `Content-Type` is a suggestion), ClamAV, metadata extraction, re-encode,
   thumbnailing.
4. **Encrypt and promote.** Generate a per-object DEK, AES-256-GCM the original
   into `S3_BUCKET_EVIDENCE`, wrap the DEK under the existing master key, delete the
   staging object.
5. **Confirm.** When the reporter clicks the email link,
   `createReportFromToken` pulls the manifest of clean attachments into the same
   transaction, inserts the `attachments` rows, and the digests land in
   `content_hash`. Anything still `pending` or `infected` at that moment is
   excluded, and the reporter is told which.

**Never do this in the app process.** ffmpeg, ImageMagick and exiftool are
memory-unsafe parsers being fed files chosen by an adversary who would very much
like this particular site to go down on election day. A malicious video that
segfaults the worker costs one queue item; the same video inside the Express
process takes the whole site offline, and anything sharing the box with it.

## 7. Encryption, and how deletion survives an append-only chain

Envelope encryption, mirroring what `src/crypto.js` already does for Tier B: a
random DEK per object, the object encrypted under it, the DEK encrypted under
the master key from `.env`. Hetzner stores ciphertext and nothing else. The
stripped metadata is encrypted under the same per-object key rather than the
master key, so destroying it takes the GPS with the pixels. The
existing README note about eventually moving to HSM or Shamir-split custody
applies here with more force, because the material at stake is now photographs
rather than an organisation name.

This buys something beyond confidentiality, and it is the answer to the hardest
question in the whole feature. An append-only evidentiary archive and a right to
erasure look irreconcilable: the chain must not change, and the data must go
away. Per-object keys dissolve that.

Null `dek_wrapped`, stamp `dek_destroyed_at`, and the content is gone beyond
recovery while the archive still says — provably, to a third party holding only
the public transparency log — that a file with that digest was submitted on that
date and later erased. The ciphertext becomes noise; the SHA-256 in the chain
and the DFN anchor over it remain intact and verifiable, so an erasure never
looks like tampering.

Retention policy then becomes a scheduled job over `attachment_heads` rather
than an architectural problem, and the unused `legal_hold` column on `reports`
finally has a job: it is what stops that job running on a given thread.

**Worth deciding early.** Client-side encryption in the browser — WebCrypto,
chunked AES-GCM, key wrapped by the server — would close the minutes-long window
where plaintext sits in the staging bucket. It also means the worker must
decrypt before it can scan, so it buys less than it first appears. Recommend
shipping server-side envelope encryption with SSE on the staging bucket, and
treating browser-side encryption as a later hardening step rather than a launch
blocker.

## 8. Moderation is the real bottleneck

The storage bill for this feature is tens of euros a month. The moderation cost
is the thing that can actually break it, and no amount of infrastructure fixes
it.

Election-week arithmetic:

| Quantity | Assumption | Result |
| --- | --- | --- |
| Reports over a 72-hour window | a busy national cycle | 25,000 |
| Carrying media | 40%, averaging 2.5 files | 25,000 files |
| Bytes ingested | ~9 MB average across photo and video | ≈ 225 GB |
| Storage cost | Object Storage list price | ≈ €1.40 / month |
| Peak-hour ingest | 8% of the window in one hour | ≈ 40 Mbit/s |
| Transcode work | ~20 CPU-seconds per video | ≈ 55 CPU-hours |
| **Human review** | **45 seconds per file** | **≈ 310 person-hours** |

Ten volunteer moderators working six-hour days clear that in five days. The
bytes arrive in three. **The queue is structurally behind from the first hour of
the event** — and that is with generous assumptions. A coordinated flood of
plausible-looking junk media aimed at exactly this bottleneck is a cheap and
obvious attack on an election-integrity site.

**Design implication.** Publish text on its own schedule and let media trail it.
A report reaching the board with *"2 files submitted, under review"* is honest,
is useful to a reader immediately, and decouples the fast path from the slow
one. The alternative — holding the whole report until its video is cleared —
converts a media backlog into a reporting blackout.

Then make the queue triageable rather than chronological: group by `incident_id`
so ten videos of one incident are one review, sort credentialed observers ahead
of anonymous submissions, and surface perceptual-hash duplicates as a single
item.

### What a moderator must do before publishing

- **See the original, audited.** Streamed through the app, decrypted in flight,
  written to `access_log` on every single view — identical to the existing Tier
  B endpoint. No presigned URL to an original, ever: a presigned URL bypasses
  every piece of middleware in the app, including the site-access gate.
- **Decide on the rendition, not the original.** What can be published is the
  stripped derivative — no GPS, no device serial, no capture timestamp beyond
  what the reporter typed into the form themselves.
- **Handle faces.** Bystanders in a polling-place photo are identifiable people
  who consented to nothing, and under GDPR that is squarely personal data. At
  minimum a blur tool in the review UI; realistically a default posture of
  *publish the report, withhold the photo* unless the photo genuinely adds
  something the narrative does not.
- **Write alt text.** Required to publish. It is an accessibility obligation,
  and it doubles as a check that someone actually looked at the file.
- **Have an escalation path.** CSAM and credible violent threats are not
  moderation decisions. They need a documented route out of the normal queue, a
  hard block on publication, and a preserved encrypted original.

One more coupling to get right: withdrawal has to take media down immediately.
Keep public rendition cache TTLs short, key URLs by digest so a new version
cannot be served from a stale cache, and treat the withdraw endpoint as a
cache-invalidation event.

## 9. What people see

### Submitting

Attach sits with the narrative, not on a separate step — evidence is part of
telling what happened. Files upload in the background while the reporter is
still typing, so the perceived cost is near zero, with per-file progress and an
explicit *"nothing is submitted until you confirm by email"* next to the file
list.

The existing PWA is a real asset here: a service worker plus IndexedDB queue
means someone can photograph an incident with no signal at all, walk away, and
have the upload complete when connectivity returns. For a poll observer standing
in a rural precinct that is the difference between capturing evidence and not.

The reporter should be told plainly, at attach time, that location and camera
metadata travel with a photo and that the public version has it removed. It is
both a privacy disclosure and a reason to trust the system with the original.

### Confirming

The email link's response already distinguishes states; it gains one more
responsibility — naming exactly which files made it into the record and which
did not, and why (*"one file could not be read"*). This is the last moment the
manifest can change, so it is the last moment to be honest about it.

### My Reports

Files appear per version, because that is what the data model says: this version
committed to these three files. Adding one later is offered, with the §4
consequence stated before the file picker opens — *"adding a file files a
correction; your report returns to review until a moderator re-approves it."*
Surprising someone into unpublishing their own report is the failure mode to
avoid.

### The public board

A published rendition shows as a thumbnail with a hash-verifiable download; an
unpublished one shows as a count and nothing else. Both states are informative.
The provenance line the board already renders is the natural home for it —
*"3 attachments, 2 published"* sits comfortably beside the corroboration count
and the severity label, and it uses the same honesty `/api/stats` already
commits to about what is being withheld.

The CSV export should carry attachment counts and digests but not URLs. A digest
is verifiable forever; a URL is a promise about hosting that this project should
not be making to a journalist re-publishing a spreadsheet.

## 10. Build order

Each phase is independently shippable and independently useful. The riskiest
infrastructure work is deliberately last, not first.

> **Where this got to, as of MK 0.0.41.** Phases 1 to 3 have all shipped,
> in a different order and more cheaply than planned. Photos, video, audio
> and PDF are all live, each kind switchable from the Admin page without a
> deploy. PDFs publish as rendered page images, as this document argues
> they must. Video transcoding runs on the same box rather than a VM of its
> own — the volume has not justified one, and that is a decision to revisit
> rather than a step that was skipped. Office formats were never built and
> are not planned. Phase 4 is still open, minus the offsite replication,
> which is done. The phases below are left as written because the reasoning
> in them is why the thing is shaped the way it is.

- **Phase 1 — images only, end to end.** Bucket setup, presigned upload, worker
  with scan and EXIF strip, both tables, manifest into `content_hash`, moderator
  approve/refuse with alt text, thumbnails on the board. JPEG/PNG/HEIC, 25 MB
  cap. Every hard architectural question gets answered here at a tenth of the
  operational weight.
- **Phase 2 — documents.** PDF and office formats. Mostly a rendering problem —
  a PDF is an active document, so publish a rasterised preview, never the
  uploaded file inline. Pairs well with getting retention and crypto-shredding
  in place.
- **Phase 3 — video.** Transcode queue on its own Hetzner VM, resumable
  multipart, poster frames, duration caps. This is where the CPU budget, the
  moderation-time budget and the worker's blast radius all actually bite.
- **Phase 4 — scale and hardening.** Offsite Borg replication to a Storage Box,
  perceptual-hash dedup, incident-grouped batch review, browser-side encryption,
  split key custody.

### Open questions worth settling before Phase 1

- **Default publication posture.** Withhold-unless-approved is the safe reading
  of the project's own privacy stance, but it means most submitted media is
  never public. Is the archive primarily *for* the public board, or is it a body
  of evidence with a public summary? The answer changes the moderation budget by
  an order of magnitude.
- **Anonymous upload quota.** Files are accepted before the email is verified. A
  tight quota risks losing genuine evidence from a reporter with a lot to show;
  a loose one is free anonymous hosting on someone else's dime.
- **Retention clock.** How long do encrypted originals live once a report is
  refused, withdrawn, or simply old? Crypto-shredding makes the mechanism easy
  and the policy question unavoidable.
- **Where the worker runs.** A second process on the shared box is simplest and
  is fine through Phase 2. Phase 3 wants its own machine — worth confirming that
  a separate Hetzner Cloud VM is acceptable before the architecture assumes it.
